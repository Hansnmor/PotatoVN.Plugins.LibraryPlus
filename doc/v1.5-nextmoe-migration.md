# v1.5.0 数据源迁移说明（kungal API → NextMoe + kungal 网页）

> 本文记录 v1.5.0 相对 v1.4.6 的数据源变更、功能对照与实现要点。
> 写于 2026-09-26，所有结论均有实测依据（命令与数据附在相应位置）。

## 1. 为什么要改

**kungal 的 HTTP API 已全站改为需登录**。任何匿名 `GET https://www.kungal.com/api/*` 都返回：

```
HTTP 401
{"code":205,"message":"用户登录失效"}
```

实测 `/api/search`、`/api/galgame/{gid}`、`/api/galgame-character/{id}`、`/api/home`、`/api/tag`、`/api/user`、`/api/auth`
全部如此；带不带 Cookie/UA/Referer 都一样，首页也不下发任何 cookie。
因此 v1.4.6 的 `KungalClient` 恒返回 `default` → 零候选 → 表现为「搜刮匹配不到任何游戏」。

**注意：网页端没有关**。`https://www.kungal.com/` 与 `/galgame/{gid}` 仍是 200 —— 这条线索是 v1.5 方案的基础。

## 2. 现在的数据来源

| 数据 | 来源 | 需要登录 |
|---|---|---|
| 作品详情（简介 / 标签 / 开发商 / 引擎 / 发行日期 / 时长 / 外部评分） | **kungal 网页 SSR** | 否 |
| **用户类型投票**（`game_types`） | **kungal 网页 SSR 的 `api:work-ratings:{gid}`** | 否 |
| **tag 的剧透标记**（`spoiler`） | **kungal 网页 SSR** | 否 |
| 角色中文名 / 头像 / 立绘 / 剧透 / voices | **kungal 网页 SSR 的 `roster`** | 否 |
| 角色简介（`intros`）与外部链接（`refs`） | NextMoe 批量水合 | **是** |
| 名称 / vndb id 搜索（匹配用） | NextMoe | **是** |

**回退**：详情优先走网页；网页不可用（改版/网络）时自动回退 NextMoe API，并打一条 Warning 说明本次会缺什么。

## 3. 网页抓取原理

### 3.1 数据藏在 Nuxt 的 SSR 载荷里

`/galgame/{gid}` 的 HTML 内含：

```html
<script id="__NUXT_DATA__" type="application/json" data-ssr="true">[…]</script>
```

键表中带 `api:` 前缀的项就是**服务端渲染时已经调用过、并把结果内嵌进来**的接口缓存，例如
`api:work:{gid}:nsfw`、`api:work-ratings:{gid}`。**匿名即可读取，绕开了 HTTP API 的登录校验。**

### 3.2 必须带 SFW 解锁 cookie

```
Cookie: KUNGalgameSettings={"showKUNGalgameContentLimit":"all"}
```

不带它只能拿到 `api:work:{gid}:sfw` 精简视图（性相关 tag 会被整批滤掉，实测 gid=49：富视图 100 个 tag / 精简视图 77 个且 `is_sexual` 全为 false）。

### 3.3 payload 是 devalue 风格的扁平数组

数组元素之间用**整数下标**互相引用：

- 容器（对象/数组）内部的元素 → 一律是下标，要继续解引用；
- 解到**基本值**（字符串/布尔/null/浮点）→ 它就是最终值，**不能再当索引**，否则无限递归。

⚠️ **两个必须遵守的约束**（都踩过）：

1. **只还原白名单键，且必须记忆化**。池里的对象是共享且互相引用的（页面里还有
   `api:wall:galgame`、`api:quizzes-work`、`api:work-resources` 等），无记忆化地全量展开会**指数爆炸**：
   实测每个键 > 200 万次展开，把进程吃到 **6.9GB 内存并卡死**；加记忆化后同一个 work 键只需 4433 次。
2. **同一个 `api:` 键会在池里出现多次**，一个是有效下标、另一个是 **`-1`（devalue 的 undefined 占位）**。
   遍历时后者会覆盖前者，**必须判 `idx >= 0`**。

### 3.4 角色独立页面不存在

`/character/{id}`、`/galgame/{gid}/character/{id}` 等路由**全部 404**；角色数据只在 galgame 页的 `roster` 里。
`roster` 含 `localized.zh-Hans` / `image` / **`figure`（立绘）** / `spoiler` / `voices`，
**缺 `intros` 与 `refs`** —— 这两样只能回头找 NextMoe。

**两边角色 id 完全同一空间**（实测 gid=49：网页 roster 21 个与 NextMoe characters 21 个，交集 21、双向无差异），
所以可以直接把网页的 roster id 喂给 NextMoe 的 `characters?ids=`。

### 3.5 搜索走不了网页（已实测否掉，别再试）

- `/search?q=` → 200，但纯客户端渲染：payload 里只有表单状态与搜索历史，0 个作品链接。
- `/galgame/search?q=` → 200，payload 里有 `api:work:search:nsfw` 这个**键**，但**值是 `-1`**，
  服务端 SSR 没有预取搜索结果，`q` 传什么都不管用。
- `/galgame?q=` 里的 `q` **不生效**，返回的是 `sort:"resource_updated_desc"` 的列表页。
- `/galgame/v{id}` 之类按 vndb id 的路径虽 200，但无法据此定位（kungal gid ≠ vndb id）。

## 4. 与 v1.4.6 的功能对照

### 唯一的功能退化：分类的「用户类型投票」—— **已于 v1.5 恢复**

kungal 的 `galgame_type` 在 NextMoe 的 work 详情里**没有**对应字段，一度导致 `TypeVotes` 恒空、
`GalgameClassifier` 第③步（投票路径）失效。

**但网页的 `api:work-ratings:{gid}` 里有 `game_types`**（`["daily"]` 这种），且实测
`data.total = 17`、`total_relation = "eq"` —— 是**完整列表、没有分页截断**。
映射进 `KungalDetail.Ratings[].GalgameType` 后，原有的按「勾 N 个类型各计 1/N」拆票逻辑**零改动**即可工作。

实测 gid=4893：`TypeVotes = {"daily":7.33,"plot":34.83,"moe":12.33,"ba_saku":0.5}`，`RatingCount:55`。

### 已修复的两处（相对 v1.4.6/中途版本）

1. **性相关 tag 混入游戏标签**：NextMoe/kungal 网站用 `is_sexual` 布尔表达性相关
   （「拔作」= `tag_kind:content` + `is_sexual:true`），而旧 kungal API 是独立的 `sexual` 类。
   不还原的话 `CleanTags()` 的 `Category == "content"` 过滤失效，体位/行为类 tag 会被写进玩家的标签列表
   （实测 gid=49 会挤进 17 个、gid=351 挤进 15 个）。现已还原成 `sexual`。
2. **同类角色重复条目**：NextMoe 常对同一角色返回两条（一条带 `zh-Hans` 中文名、一条只有原名，
   如 gid=49 的 497 与 237990 同名）。不合并则"没中文名的那条"会被判成无链接 →
   触发整轮 bgm 兜底往返（实测吃 26 秒）。现按归一化角色名去重，同组优先保留有中文名的那条。

### 仍然存在的限制

- **tag 的剧透过滤**：网页侧能拿到 `spoiler: minor/major`（实测 6 个），**已恢复**；
  但若走 NextMoe 回退路径则该字段全为 `none`（NextMoe 的 tag spoiler 一律 none），此时过滤失效。
- **纯汉字日文名会被当中文名写入**（如「加鳥周平」「島田 辰子」）：`IsJapaneseName` 只能识别假名，
  这是 v1.4.6 就有的既有行为，非本次迁移引入。**不建议用「日文专用汉字表」去修** ——
  繁体中文里「島」「澤」也是正常写法，会误伤繁中作品。

## 5. 账号与本插件的关系（重要）

**kungal 与 NextMoe 是同一套账号系统**：`https://www.kungal.com/` 首页的账号入口就是
`href="https://account.nextmoe.com/"`（还链到 `docs-kungal.nextmoe.dev`）。

所以对**本插件的目标用户**（已知 kungal 的人）而言，「登录 NextMoe」等于「用你已有的 kungal 账号授权」，**没有额外注册成本**。
OAuth 只需授权一次，refresh token 用 DPAPI（CurrentUser）加密存盘、长期有效。

**未登录时的影响面**：

- ✅ 详情、简介、标签、剧透过滤、类型投票、角色中文名/立绘/剧透 —— 全部正常（走网页）
- ❌ 新游戏的匹配（搜索走 NextMoe）
- ❌ 角色简介、角色外链

有 gid 记忆的老游戏不受影响（匹配第一层「ID 记忆」不需要网络）。
未登录导致匹配失败时会打一条明确的 Warning 指引去登录。

## 6. 代码结构

```
Helper/KungalWeb/           ← v1.5 新增：kungal 网站抓取
  KungalWebClient.cs        抓页面 + 抠 __NUXT_DATA__ + 还原（含记忆化与白名单）
  KungalWebMapper.cs        网页结构 → KungalDetail（含 is_sexual→sexual、game_types→Ratings）
Helper/NextMoe/             ← v1.5 新增：NextMoe 开放 API v2
  NextMoeModels.cs          数据模型（含吸收 {lang,value,is_machine} 对象与 [lang,value] 数组两种形状的转换器）
  NextMoeClient.cs          HTTP 客户端（令牌桶节流、无信封反序列化、problem+json 错误日志）
  NextMoeKungalAdapter.cs   对 KungalPhraser 暴露与旧 KungalClient 相同的三个签名
  NextMoeAuth.cs            OAuth 授权码 + PKCE、TcpListener 环回回调、DPAPI 加密存 refresh token
Helper/Kungal/
  KungalPhraser.cs          匹配与写回（换源只改了 _client 的类型，匹配逻辑未动）
  KungalModels.cs           KungalCard 加了非 JSON 字段 ExactRefMatch
doc/nextmoe/                官方文档快照（llms.txt / v2.md / native-app.md / authentication.md 等）
```

`KungalPhraser` 的三个调用点（`SearchAsync` / `GetDetailAsync` / `GetCharacterAsync`）签名不变，
所以**匹配、字段保护、角色中文名解析等逻辑一行未改**。

## 7. 性能

| 场景 | v1.4.6（kungal API 可用时） | v1.5 |
|---|---|---|
| 单款（短篇，页面 427KB） | — | 约 3.6s |
| 单款（长篇，页面 1.3MB，35 角色） | — | 约 3.6s |
| 中途版本（网页抓取刚接入，有 N+1 与串行节流） | — | 31s（已优化） |

优化点：角色详情批量水合（一次 `characters?ids=` 取代 N 次单查）、令牌桶节流取代串行等待、
详情 5 分钟缓存、网页抓取限速 600ms、启动时后台预热 NextMoe 令牌（避免首次搜刮现刷 token）。
